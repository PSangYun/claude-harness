# /logic — 동작 구현 (2단계: 기능, API 연결 금지)

입력: Figma 디스크립션 URL 또는 기능정의서 + 대상 도메인명. 1단계(/design)에서 만든 UI에 동작을 붙인다. **API 연결은 3단계의 일** — 이 단계에서는 스텁까지만.

## Phase A: 디스크립션 분석

1. 디스크립션/기능정의서의 동작 항목을 **전수 목록화**: `[동작]`, `[필수 입력]`, `[검증 규칙]`, `[수정 시 다른 점]`, `[에러 케이스]`
2. 각 항목에 대해 `동작 | 트리거 | 상태 변화 | 구현 위치(VM/View)` 표 작성
3. 애매한 항목은 추측하지 말고 사용자에게 질문

## Phase B: 상태·시그니처 정의

- VM에 상태(`@Published`)와 액션 함수 시그니처를 확정 (1단계 더미를 실제 상태 모델로 교체)
- API가 필요한 지점은 **빈 함수 + `// TODO: connect-api (3단계)`** 로 스텁 — 네트워크 코드 작성 금지
- 화면 간 전달 데이터는 타입으로 명시

## Phase C: 동작 구현

- 입력 검증, 상태 전이, 조건부 노출/비활성화, 화면 전환(기존 네비게이션 패턴 준수)
- 에러/빈 상태 처리 (기존 패턴: AppMsgState·Toast 등 ios-common/프로젝트 공통 사용)
- 비즈니스 로직은 **VM에** — View에는 바인딩만

## Phase D: 자가 확인

- 빌드 성공 (xcodebuild) + SwiftLint(있으면) 위반 0
- 테스트 타겟이 있으면 순수 로직(상태 전이·검증 규칙) 테스트 작성 후 통과 (test-writer 규칙 준수)

## Definition of Done

1. Phase A 동작 목록이 전수 구현됨 (목록 ↔ 구현 대조표 근거)
2. API 지점은 전부 TODO 스텁 — 신규 네트워크 호출 코드 0건
3. 비즈니스 로직이 VM에 있음 (View에는 바인딩/레이아웃만)
4. 입력 검증·에러 상태 처리 구현됨 (디스크립션의 에러 케이스 전수)
5. 빌드 성공 (xcodebuild 실행 결과)
6. 신규 코드에 `print()`·강제 언래핑 0건

> **완료 선언 전 checker 서브에이전트의 PASS 판정 필수** (maker/checker 분리 — 글로벌 규약).
