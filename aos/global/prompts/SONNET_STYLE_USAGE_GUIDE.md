# 프롬프트 패키지 사용 가이드 — Sonnet판 (Claude Code CLI)

이 패키지는 Opus용 패키지(`OPUS_4_8_STYLE_*`)와 같은 운영 규칙을 Sonnet 계열 모델(Sonnet 4.5, Sonnet 5 등)에서도 안정적으로 작동하게 조정한 파생판이다. 규칙의 내용은 같고, 중형 모델에서 자주 무너지는 지점(조기 완료 선언, 다항목 축약, 테스트 약화, 에러 은폐, 과잉 포맷, 반사적 동의)에 금지 문장과 ❌/✅ 예시, 종료 전 자가 점검 게이트를 보강했다.

| 파일 | 용도 |
|---|---|
| `SONNET_STYLE_SYSTEM_PROMPT.md` | 메인 프롬프트. 시스템/상위 지시로 주입 |
| `SONNET_STYLE_COMPACT_PROMPT.md` | 압축판. 토큰이 아쉬운 컨텍스트용 |
| `SONNET_STYLE_USAGE_GUIDE.md` | 이 문서. 배치·운영 방법 |
| `SONNET_STYLE_EVAL_CHECKLIST.md` | 프롬프트가 실제로 작동하는지 검증하는 체크리스트 (J절 = Sonnet 특화 항목) |

## 0. Opus 패키지와의 관계

- **원본은 Opus판, 이 패키지는 파생판이다.** 규칙 내용을 바꿀 때는 Opus 메인판을 먼저 고치고, 그 변경을 이 패키지에 반영하면서 Sonnet용 보강(예시·금지 문장)을 함께 조정한다.
- **한 세션에는 한 패키지만 주입한다.** Opus 세션에는 OPUS 파일, Sonnet 세션에는 SONNET 파일. 두 판을 같은 컨텍스트에 함께 넣으면 중복 규칙이 서로 드리프트해 준수율이 오히려 떨어진다.
- 절 번호(0~13절)는 두 판이 동일하게 정렬되어 있어 체크리스트 FAIL 기록·문구 비교를 판 간에 그대로 대조할 수 있다. 14절(자가 점검)과 체크리스트 J절은 Sonnet판에만 있다.

## 1. Claude Code CLI에 주입하는 방법

우선순위가 높은 방법부터 나열한다. 하나만 선택한다 — 같은 내용을 두 경로로 이중 주입하면 토큰 낭비이자 규칙 드리프트의 원인이 된다.

### 방법 A — 시스템 프롬프트로 직접 주입 (권장)

메인 프롬프트를 시스템 레벨 지시로 넣는 방법. 주입 경로 중 가장 상위 위치라 규칙이 컨텍스트에서 밀려나거나 잘릴 위험이 가장 적다. **Sonnet은 규칙이 컨텍스트 후방으로 밀렸을 때 준수율 하락이 Opus보다 가파르므로, Sonnet에서는 특히 이 방법을 권장한다.**

```bash
# 일회성 세션 (bash/zsh)
claude --model sonnet --append-system-prompt "$(cat prompts/SONNET_STYLE_SYSTEM_PROMPT.md)"

# 셸 alias로 상시화 (~/.bashrc, ~/.zshrc)
alias ccs='claude --model sonnet --append-system-prompt "$(cat ~/prompts/SONNET_STYLE_SYSTEM_PROMPT.md)"'
```

```powershell
# PowerShell $PROFILE에 함수로 상시화 (Windows)
function ccs {
    $rules = Get-Content "$HOME\prompts\SONNET_STYLE_SYSTEM_PROMPT.md" -Raw
    claude --model sonnet --append-system-prompt $rules @args
}
```

- `--append-system-prompt`는 기본 시스템 프롬프트를 유지한 채 뒤에 덧붙인다. Claude Code의 내장 도구 사용 규칙을 깨뜨리지 않으므로 이쪽을 쓴다.
- 전체 교체 옵션(`--system-prompt`)은 내장 도구 안내까지 지워 오히려 품질을 떨어뜨릴 수 있으므로, 다른(비 Claude Code) 하네스에서 시스템 메시지를 처음부터 구성할 때만 고려한다.
- `--model sonnet`을 alias에 함께 넣어 두면 "Sonnet 세션 = SONNET 규칙"이 강제되어 패키지가 섞이지 않는다. Opus용 alias(예: `cc`)와 분리해 운영한다.

### 방법 B — 전역 `~/.claude/CLAUDE.md`에 배치

CLI 플래그를 관리하기 번거로우면 메인 프롬프트 내용을 전역 CLAUDE.md에 넣는다. 모든 프로젝트에 자동 적용된다.

- **주의: 전역 CLAUDE.md는 모델과 무관하게 모든 세션에 로드된다.** Opus와 Sonnet을 오가며 쓴다면 전역에는 한 판만 두어야 한다. 이 경우 두 가지 절충이 있다:
  - 전역에 Sonnet판을 두는 방법 — 0절의 모델-판 짝맞춤 원칙의 의도적 예외다. Sonnet판은 Opus판의 상위집합(보강판)이라 Opus 세션에 들어가도 해가 없다. 토큰을 조금 더 쓰는 대신 관리가 단순하다. 단, 이 구성에서는 방법 A의 alias 주입(Opus용 포함)을 함께 쓰지 않는다 — 전역판 + 시스템 프롬프트판의 이중 주입이 된다.
  - 전역에는 아무 판도 두지 않고 방법 A(모델별 alias)로만 주입하는 방법 — 모델별로 정확한 판이 들어가는 가장 깔끔한 구성.
- 전역 CLAUDE.md가 이미 있다면 **통째로 덧붙이지 말 것**. 기존 규칙과 겹치는 절(파일 작업, git, 응답 방식 등)은 한쪽으로 통합한다. 같은 주제의 규칙이 두 곳에 있으면 모델이 어느 쪽을 따를지 불안정해진다.
- 전역 파일이 길어질수록 매 세션 고정 토큰 비용이 늘어난다. 다만 Sonnet에서는 압축 절약분보다 예시 소실로 인한 준수율 하락 비용이 더 큰 경우가 많다(4절 참조).

### 방법 C — 프로젝트 `CLAUDE.md`에 배치

특정 저장소에서만 이 규약을 쓰고 싶을 때. 프로젝트 루트의 `CLAUDE.md`에서 `@경로` import 문법으로 참조한다.

```markdown
<!-- CLAUDE.md 상단 -->
@prompts/SONNET_STYLE_SYSTEM_PROMPT.md

## 이 프로젝트 고유 규칙
...
```

`@경로` import 문법을 쓰면 파일 분리를 유지한 채 참조할 수 있어 관리가 쉽다. 적용 후 세션에서 규칙 하나(예: 14절 자가 점검 항목)를 인용하게 해 실제로 로드되는지 한 번 확인해 둔다.

### 방법 D — 다른 모델·하네스에서 사용

Claude Code가 아닌 CLI 에이전트(또는 API 직접 호출)에서 쓸 때:

- API의 system 메시지에 메인 프롬프트 전문을 넣는다.
- 해당 하네스의 규칙 파일 관례(`AGENTS.md`, `.cursorrules` 등)가 있으면 이 판의 메인판(가능하면) 또는 압축판을 그 형식에 맞춰 넣는다.
- 도구 이름은 일반화되어 있으므로(예: "Glob/Grep/Read/Edit 류") 하네스별 실제 도구명으로 치환하면 더 정확히 작동한다.
- Sonnet급이 아닌 다른 중소형 모델에도 이 판(Opus판이 아니라)을 기반으로 시작하는 편이 낫다 — 보강의 방향이 "추상 원칙 → 행동 문장 + 예시"라서 모델이 작아질수록 유효하다. 결과 품질은 `SONNET_STYLE_EVAL_CHECKLIST`로 측정해 문구를 조정한다.

## 2. 계층별 배치 전략

규칙은 "가장 좁은 유효 범위"에 두는 것이 원칙이다. 전역에 둘수록 모든 세션이 토큰 비용을 내고, 프로젝트와 무관한 규칙이 판단을 흐린다.

| 계층 | 위치 | 넣을 내용 |
|---|---|---|
| 전역 | `~/.claude/CLAUDE.md` | 언어, 톤, 파일 작업 원칙, git 원칙, 위험 작업 목록 — 모든 프로젝트 공통 규칙 |
| 프로젝트 | `<repo>/CLAUDE.md` | 이 저장소의 아키텍처, 빌드·테스트 명령, 컨벤션, 반복 실수 기록 |
| 하위 디렉토리 | `<repo>/<dir>/CLAUDE.md` | 그 모듈에서만 유효한 규칙 (예: `app/` 전용, `server/` 전용) |
| 세션 | `--append-system-prompt` | 방법 A의 메인 프롬프트 상시 주입, 또는 실험 중인 규칙 |

운영 원칙:

- **중복 금지.** 같은 규칙을 전역과 프로젝트에 모두 쓰지 않는다. 프로젝트 규칙은 전역 규칙에 "추가"되는 것이지 반복하는 것이 아니다.
- **충돌은 구체성이 이기도록.** 전역과 프로젝트가 충돌하면 프로젝트 파일에서 명시적으로 재정의한다("전역 규칙 X와 달리 이 프로젝트는 Y").
- **규칙의 승격 흐름.** 세션에서 반복 지시하게 되는 내용 → 프로젝트 CLAUDE.md로, 여러 프로젝트에서 반복되는 내용 → 전역으로 승격한다. 반대로 한동안 쓰이지 않은 규칙은 내려서 정리한다.
- **Sonnet 전용 승격 단계가 하나 더 있다**: 프롬프트 문구를 아무리 보강해도 같은 FAIL이 반복되면(체크리스트 채점 기준 참조), 규칙을 훅(pre/post tool, stop 훅)으로 옮겨 기계적으로 강제한다. Opus에서는 문구로 충분한 규칙이 Sonnet에서는 훅이 필요한 경우가 있다.

## 3. Android/Kotlin/Compose 프로젝트 권장 배치

메인 프롬프트의 13절(Android 모듈)은 조건부 규칙이므로, 배치는 아래를 권장한다.

```
~/.claude/CLAUDE.md              ← (선택) 범용 규칙. 모델별 alias 운영 시 비워도 됨
세션 alias (ccs)                 ← SONNET 메인판 상시 주입 (방법 A)
<repo>/CLAUDE.md                 ← 13절 전문 + 프로젝트 고유 내용
<repo>/app/CLAUDE.md             ← (선택) UI 레이어 전용 규칙
<repo>/core/*/CLAUDE.md          ← (선택) 모듈별 규칙
```

프로젝트 `CLAUDE.md`에 함께 적어야 효과가 큰 항목:

- **빌드·검증 명령을 정확한 문자열로**: `./gradlew :app:compileDebugKotlin`, `./gradlew lint`, 테스트 태스크. "빌드해서 확인" 같은 모호한 문장보다 명령 원문이 실행률을 훨씬 높인다. Sonnet에서는 이 차이가 특히 크다 — 명령이 없으면 검증을 건너뛰고 완료를 선언하는 회귀(체크리스트 D1·J8)가 먼저 나타난다.
- **레이어 지도**: 패키지 구조(예: `data/dto`, `domain/model`, `ui/model`)와 각 레이어 모델의 매핑 위치. 13절의 "DTO/domain/UI 혼동 금지"는 이 지도가 있을 때 실제로 작동한다.
- **DI·Navigation 관례**: 모듈 등록 위치, 화면 추가 시 수정해야 하는 파일 목록.
- **version catalog 경로**: `gradle/libs.versions.toml` 등 의존성 선언의 단일 출처.
- **디자인 시스템 규칙**: 색상·폰트·간격 토큰 사용 강제, 하드코딩 금지 항목. 디자인 토큰 매핑 테이블이 있다면 프로젝트 CLAUDE.md가 제자리다.
- **반복 실수 기록 섹션**: 같은 실수가 재발할 때마다 날짜와 함께 추가한다. 프롬프트 규칙 중 가장 투자수익이 높은 부분이다.

멀티모듈 프로젝트에서 특정 모듈만 규칙이 다르면(예: 공용 라이브러리 모듈은 공개 API 변경 시 확인 필수) 그 모듈 디렉토리의 CLAUDE.md에 넣는다.

## 4. 메인판 vs 압축판 선택 기준

Opus판과 달리 **Sonnet에서는 메인판이 기본값이다.** 보강의 핵심(❌/✅ 예시, 금지 문장, 14절 게이트)이 압축 과정에서 가장 먼저 깎이는 부분인데, Sonnet의 준수율은 바로 그 부분에 의존한다.

- **메인판**: 방법 A 시스템 프롬프트 주입(권장 기본), 규칙 위반이 관찰되는 모든 경우, 장기 세션.
- **압축판**: 프로젝트 CLAUDE.md가 이미 매우 길어 컨텍스트가 빠듯할 때, 또는 컨텍스트 창이 작은 환경일 때만.
- 압축판으로 운영하다 체크리스트에서 FAIL이 나오면, 프롬프트 전체를 바꾸기 전에 **FAIL이 난 절만 메인판 문구(예시 포함)로 교체**하는 점진 확장이 토큰 대비 효율이 좋다.

## 5. 유지보수

- 규칙을 바꿀 때의 반영 순서: **Opus 메인판(원본) → Sonnet 메인판(이 패키지, 예시·금지 문장 보강 포함) → 각 압축판**. Sonnet판에서만 발견된 개선(새 실패 모드에 대한 금지 문장 등)은 Sonnet판에 먼저 넣되, 모델 공통으로 유효하면 Opus판으로 역승격한다.
- **Sonnet은 체크리스트를 더 자주 돌린다.** Opus판의 분기별 점검에 더해, Sonnet 모델 버전이 바뀔 때마다(예: 4.5 → 5) J절 전체 + 직전 라운드 FAIL 항목을 최소로 돌린다. 중형 모델은 버전 간 행동 변화 폭이 커서 프롬프트 민감도가 함께 변한다.
- 규칙이 지켜지지 않을 때의 점검 순서: ① 같은 주제의 규칙이 여러 파일에 중복/충돌하는지(특히 Opus판과 이중 주입 여부) → ② 규칙이 추상적 원칙에 그치고 실행 가능한 행동 문장이 아닌지 → ③ 압축판 사용 중이라면 해당 절을 메인판으로 교체 → ④ 컨텍스트 과밀로 규칙이 밀려나는지 → ⑤ 그래도 반복되면 훅으로 기계적 강제.
